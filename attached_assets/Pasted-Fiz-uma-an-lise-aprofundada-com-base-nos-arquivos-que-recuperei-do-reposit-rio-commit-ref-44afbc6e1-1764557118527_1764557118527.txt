Resumo do problema principal encontrado (falha do CI)
- Erro no CI: tsc --noEmit falhando com TS2589: "Type instantiation is excessively deep and possibly infinite" em várias páginas (Agents.tsx, ModulesAdmin.tsx, Namespaces.tsx) tanto em apps/frontend-service quanto em client.
- Causa provável: inferência de tipos muito profunda/recursiva — comumente causada por:
  - Tipos gerados a partir de schemas (zod.infer combinado com muitas composições).
  - Uso de generics sem anotações explícitas (useQuery, useMutation, helpers apiRequest sem tipos explícitos).
  - Props de componentes com tipos complexos que propagam a inferência.
- Observação: em algumas versões dos arquivos já há comentários/ajustes tentando "definir interface explicitamente primeiro para evitar TS2589" — boa direção, mas ainda há pontos sem anotações explícitas que continuam a forçar a inferência do compilador.

Revisão técnica detalhada e recomendações (com correções propostas)

1) Corrigir TS2589 — prática recomendada geral
- Estratégia: reduzir inferência automática em pontos críticos adicionando tipos explícitos (interfaces/aliases) antes de usar zod.infer/useForm/useQuery/useMutation. Isto evita que o compilador expanda tipos recursivos.
- Exemplos concretos de correção:
  - Definir a interface do formulário antes do schema zod e tipar explicitamente o z.object com ZodType<Interface>.
  - Tipar useForm com o tipo explícito: useForm<AgentFormData>({ resolver: zodResolver(agentFormSchema) })
  - Tipar useQuery e useMutation: useQuery<Agent[], Error>(...) e mutações: useMutation<Agent, Error, Partial<AgentFormData>>(…).

Exemplo aplicado (snippet sugerido para Agents.tsx — inicialização do form e queries):
```typescript name=apps/frontend-service/src/pages/Agents.tsx url=https://github.com/fillipeguerrabtc/alice/blob/44afbc6e1b5467ba7e371db4e070aea0a281f4c6/apps/frontend-service/src/pages/Agents.tsx
// Trecho sugerido: tipagem explícita para schema + useForm + useQuery
interface AgentFormData {
  nome: string;
  slug: string;
  status: "active" | "training" | "paused" | "deprecated";
  descricao?: string | null;
  instrucoes?: string | null;
  personalidade?: string | null;
}

const agentFormSchema: z.ZodType<AgentFormData> = z.object({
  nome: z.string().min(2),
  slug: z.string().min(2).regex(/^[a-z0-9-]+$/),
  status: z.enum(["active", "training", "paused", "deprecated"]),
  descricao: z.string().nullable().optional(),
  instrucoes: z.string().nullable().optional(),
  personalidade: z.string().nullable().optional(),
});

// Tipar useForm explicitamente para quebrar inferência profunda
const form = useForm<AgentFormData>({
  resolver: zodResolver(agentFormSchema),
  defaultValues: {
    nome: "",
    slug: "",
    status: "active",
  },
});

// Tipar useQuery e api calls
const { data: agents } = useQuery<Agent[], Error>(["agents"], () => apiRequest<Agent[]>("/api/agents"));
```

2) Tipar apiRequest / queryClient para reduzir inferência do TS
- Se a função apiRequest retorna Promise<any> com inferência dinâmica, o compilador tentará propagar tipos complexos. Forneça assinatura genérica simples:
```typescript name=apps/frontend-service/src/lib/queryClient.ts url=https://github.com/fillipeguerrabtc/alice/blob/44afbc6e1b5467ba7e371db4e070aea0a281f4c6/apps/frontend-service/src/lib/queryClient.ts
export async function apiRequest<T = unknown>(input: string, init?: RequestInit): Promise<T> {
  const res = await fetch(input, init);
  if (!res.ok) throw new Error(await res.text());
  return (await res.json()) as T;
}
```
- Em todos os pontos onde apiRequest é usado, invoque como apiRequest<MyType>(url) e tipar useQuery/useMutation explicitamente.

3) Zod + react-hook-form: preferir ZodType explícito e não usar z.infer em schemas grandes
- Já há progressos no código (definindo ZodType<T>), mantenha essa abordagem em todos os schemas (Forms, DTOs, respostas de API).
- Evite zod.infer em objetos muito complexos e, quando necessário, extraia interfaces simplificadas para uso em componentes.

Patch/trechos sugeridos (aplicáveis imediatamente)

1) apiRequest (tipagem genérica)
```typescript name=apps/frontend-service/src/lib/queryClient.ts url=https://github.com/fillipeguerrabtc/alice/blob/44afbc6e1b5467ba7e371db4e070aea0a281f4c6/apps/frontend-service/src/lib/queryClient.ts
export async function apiRequest<T = unknown>(path: string, opts?: RequestInit): Promise<T> {
  const res = await fetch(path, {
    headers: { 'Content-Type': 'application/json' },
    ...opts,
  });
  const text = await res.text();
  let data;
  try {
    data = text ? JSON.parse(text) : null;
  } catch {
    throw new Error(`API returned non-JSON response (${res.status}): ${text}`);
  }
  if (!res.ok) {
    throw new Error(data?.message || `Request failed: ${res.status}`);
  }
  return data as T;
}
```

Notas finais — justificativa e impacto
- O erro TS2589 é sintoma de definição de tipos muito complexa que atinge limites do TypeScript — corrigi-lo exige reduzir a inferência automática em pontos-chaves. As correções propostas (tipagem explícita, ZodType<T>, generics em apiRequest/useQuery) são de baixo risco e permitem que o compilador processe rapidamente os tipos.
- Aplicar as mudanças pequenas e iterativas (um arquivo por vez) facilitará encontrar o ponto exato que fazia o tsc travar. Também melhora a qualidade do código e previne regressões.
