Resumo executivo (rápido)
- Causa primária do CI break: TS2589 "Type instantiation is excessively deep and possibly infinite" causado pela inferência recursiva do TypeScript ao combinar zodResolver (do @hookform/resolvers) com a tipagem genérica do react-hook-form em arquivos grandes (Agents.tsx, ModulesAdmin.tsx, Namespaces.tsx — e cópias em client/).
- Correção prática, segura e mínima: forçar a tipagem do resolver para react-hook-form's Resolver<T> com um cast (zodResolver(...) as unknown as Resolver<T>). Isso impede que o TypeScript expanda recursivamente os tipos internos do zod/resolvers e resolve imediatamente o erro de compilação sem perda significativa de segurança de tipos no nível do formulário.
- Mitigação adicional: manter apiRequest (que retorna Response) como está para endpoints de streaming; adicionar helper apiJson<T>() para chamadas JSON onde queremos parsing direto e tipado. Isso evita mudanças que quebrem streaming de chat.

5) Pequena melhoria em queryClient: adicionar apiJson<T> helper
Motivação: não quero mudar apiRequest (ele retorna Response) porque endpoints de streaming (chat SSE/fetch stream) consomem res.body. Ao mesmo tempo, muitas chamadas fazem res = await apiRequest(...); return res.json(); — podemos oferecer um helper tipado para respostas JSON e incentivar seu uso. Isso melhora segurança de tipo e evita uso incorreto do any.

Proposta de adição (mantendo apiRequest como está):
```ts name=apps/frontend-service/src/lib/queryClient.ts url=https://github.com/fillipeguerrabtc/alice/blob/44afbc6e1b5467ba7e371db4e070aea0a281f4c6/apps/frontend-service/src/lib/queryClient.ts
// --- adicionar abaixo das funções existentes ---

/**
 * Helper para requests que retornam JSON e queremos já obter T tipado.
 * Usa internamente apiRequest (que retorna Response), preservando streaming/low-level quando necessário.
 */
export async function apiJson<T = unknown>(method: string, url: string, data?: unknown): Promise<T> {
  const res = await apiRequest(method, url, data);
  // Caso preciso tratar status 204/empty, adaptamos aqui:
  if (res.status === 204) return undefined as unknown as T;
  const text = await res.text();
  if (!text) return undefined as unknown as T;
  try {
    return JSON.parse(text) as T;
  } catch (err) {
    // fallback para res.json() se possível
    return (await (res.clone().json())) as T;
  }
}
```

Quando usar apiJson:
- Para endpoints normais CRUD (lista de agents, criar namespace, etc) prefira:
  const agents = await apiJson<Agent[]>('GET', '/api/agents');
- Para endpoints de streaming (chat/stream) mantenha apiRequest(...) e leia res.body.

6) Raciocínio técnico e por que a solução é segura
- O erro TS2589 não é um bug do projeto, é o TypeScript atingindo limite de expansão de tipos em tipos muito complexos (combinação de mappings de zod -> zodResolver -> resolver generics do react-hook-form). Casting do resolver para Resolver<T> é prática usada amplamente como mitigação imediata: preserva a interface do formulário (validação/segurança) e evita a expansão infinita.
- Casts são localizados (apenas no ponto do useForm), portanto impacto mínimo. Futuramente, após upgrades de TS + @hookform/resolvers + react-hook-form (quando esses pacotes tiverem tipos melhores), você pode remover os casts.
