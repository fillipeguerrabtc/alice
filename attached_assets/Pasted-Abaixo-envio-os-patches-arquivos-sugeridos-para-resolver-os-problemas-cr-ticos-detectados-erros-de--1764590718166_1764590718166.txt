1) Novo arquivo: packages/shared-utils/src/dbHealth.ts
```typescript name=packages/shared-utils/src/dbHealth.ts url=https://github.com/fillipeguerrabtc/alice/blob/main/packages/shared-utils/src/dbHealth.ts
import type { Pool } from 'pg';
import pino from 'pino';

const logger = pino().child({ module: 'shared-utils/dbHealth' });

/**
 * isPoolHealthy - verifica saúde do pool PostgreSQL.
 * - Faz connection com timeout configurável
 * - Executa SELECT 1 com timeout
 * - Sempre libera o client
 * - Retorna boolean e loga via Pino
 *
 * Uso recomendado (startup): await isPoolHealthy(pool, 2000) => se false, retry/backoff ou fail-fast em produção.
 */
export async function isPoolHealthy(pool: Pool, timeoutMs = 2000): Promise<boolean> {
  if (!pool) {
    logger.error('isPoolHealthy called without pool instance');
    return false;
  }

  try {
    // connect com timeout
    const client = await Promise.race([
      pool.connect(),
      new Promise<never>((_, rej) => setTimeout(() => rej(new Error('db connect timeout')), timeoutMs)),
    ]) as Awaited<ReturnType<Pool['connect']>>;

    try {
      // query simples com timeout
      await Promise.race([
        client.query('SELECT 1'),
        new Promise<never>((_, rej) => setTimeout(() => rej(new Error('db query timeout')), timeoutMs)),
      ]);
      logger.debug('DB pool healthy');
      return true;
    } finally {
      client.release();
    }
  } catch (err) {
    logger.warn({ err }, 'DB pool not healthy');
    return false;
  }
}
```

Explicação didática
- Objetivo: prover um utilitário reutilizável e testável para verificar se o pool de conexões PostgreSQL está funcional.
- Por quê: os erros TS2304 indicam que a função foi usada mas não existe/exportada. Essa implementação cumpre o contrato descrito no replit.md (gestão de lifecycle do pool) e evita soluções in-memory ou hardcoded.
- Como testar:
  - Unit test usando um pool real em ambiente de teste (ou mock com sinon) para simular connect ok/timeout/erro.
  - No startup dos serviços, invocar e falhar-fast em produção se retornar false (conforme regra 6 do replit.md).

2) Novo arquivo: packages/shared-utils/src/shutdownManager.ts
```typescript name=packages/shared-utils/src/shutdownManager.ts url=https://github.com/fillipeguerrabtc/alice/blob/main/packages/shared-utils/src/shutdownManager.ts
export type ShutdownHandler = () => Promise<void> | void;

class ShutdownManager {
  private handlers = new Map<number, ShutdownHandler[]>();
  private shutting = false;
  private timeoutMs = Number(process.env.SHUTDOWN_TIMEOUT_MS) || 30_000;

  /**
   * Registra handler para shutdown.
   * priority: menor número = executado primeiro (ex.: 0 = infra critical, 100 = non-critical)
   */
  register(priority: number, handler: ShutdownHandler) {
    const arr = this.handlers.get(priority) ?? [];
    arr.push(handler);
    this.handlers.set(priority, arr);
  }

  /**
   * Inicializa listeners nos sinais do processo. Idempotente.
   */
  async initializeShutdownManager() {
    if ((process as any).__shutdownManagerInitialized) return;
    (process as any).__shutdownManagerInitialized = true;

    const run = async (signal: string) => {
      if (this.shutting) return;
      this.shutting = true;
      // Use console aqui por ser chamado durante bootstrap; em runtime, substituir por logger se disponível.
      console.info(`[ShutdownManager] recebido ${signal}, iniciando graceful shutdown`);

      const priorities = Array.from(this.handlers.keys()).sort((a, b) => a - b);
      const start = Date.now();

      for (const p of priorities) {
        const handlers = this.handlers.get(p) ?? [];
        for (const h of handlers) {
          try {
            await Promise.race([
              (async () => await h())(),
              new Promise<never>((_, rej) => setTimeout(() => rej(new Error('shutdown handler timeout')), this.timeoutMs)),
            ]);
          } catch (err) {
            console.error('[ShutdownManager] erro em handler:', err);
          }
        }
      }

      const elapsed = Date.now() - start;
      console.info(`[ShutdownManager] shutdown completo em ${elapsed}ms`);
      // Forçar exit após handlers
      process.exit(0);
    };

    process.once('SIGINT', () => run('SIGINT'));
    process.once('SIGTERM', () => run('SIGTERM'));
  }
}

export const shutdownManager = new ShutdownManager();
export const initializeShutdownManager = shutdownManager.initializeShutdownManager.bind(shutdownManager);
export const registerShutdownHandler = shutdownManager.register.bind(shutdownManager);
```

Explicação didática
- Objetivo: implementar o ShutdownManager documentado em replit.md.
- Por quê: sem este componente, não há coordenação de shutdown entre serviços e recursos (DB, caches, filas), o que pode levar a corrupção ou perda de dados em produção.
- Design:
  - Registro por prioridade (ordem controlada).
  - Timeout por handler para evitar bloqueio indefinido.
  - Idempotência na inicialização.
  - Simples e integrado com Pino/console logging.
- Como usar: no bootstrap do serviço, chamar initializeShutdownManager() e registrar handlers (ex.: fechar listeners WebSocket, fechar pool DB, flush caches).

5) Patches para serviços que usavam isPoolHealthy (ex.: apps/chat-service/src/index.ts)
Exemplo de alteração a aplicar em cada serviço (chat-service, rag-service, training-service). O objetivo é: adicionar o import e fazer verificação de saúde do DB antes de iniciar o HTTP/WebSocket server.

```typescript name=apps/chat-service/src/index.ts url=https://github.com/fillipeguerrabtc/alice/blob/main/apps/chat-service/src/index.ts
// --- patch: importar isPoolHealthy e usá-lo no bootstrap ---
import { isPoolHealthy } from '@alice/shared-utils';
import { initializeShutdownManager, registerShutdownHandler } from '@alice/shared-utils';

// ... código existente de inicialização ...

async function start() {
  // inicializa o shutdown manager logo no começo do processo
  await initializeShutdownManager();

  // inicializar pool (exemplo)
  // const pool = createPgPool(...);

  // verificar saúde do pool antes de iniciar listeners em produção
  const healthy = await isPoolHealthy(pool, Number(process.env.DB_HEALTH_TIMEOUT_MS) || 2000);
  if (!healthy) {
    // Em produção, fail-fast é preferível (conforme regra 6)
    console.error('ERRO: DB pool não saudável; abortando startup');
    process.exit(1);
  }

  // registrar handler para fechar pool durante shutdown
  registerShutdownHandler(10, async () => {
    try {
      await pool.end();
    } catch (err) {
      console.error('Erro ao fechar pool no shutdown', err);
    }
  });

  // iniciar servidor WebSocket/HTTP
  // server.listen(...)
}

start().catch((err) => {
  console.error('Erro no startup', err);
  process.exit(1);
});
```

Explicação didática
- Por quê: protege contra iniciar serviços dependentes do DB quando o DB está inoperante, evitando perda de mensagens/requests.
- Onde aplicar: em todos os serviços que mantêm um pool de DB (chat-service, rag-service, training-service).
- Teste: simular DB down e verificar que o processo aborta com exit code 1 (fail-fast). Em staging, use process supervisor (systemd/container) para reiniciar conforme políticas.

7) Export additions e pequenas notas sobre tsconfig.json
- Recomendação: manter "strict": true em tsconfig.json (conforme regra 8). Não fazer downgrades permanentes.
- Se necessário por dependências externas (não por código próprio), adicionar temporariamente "skipLibCheck": true no tsconfig.json root para acelerar correções — mas somente como mitigação de curto prazo e com plano de remover depois que dependências forem atualizadas.

Exemplo de alteração (opcional e discutível) — tsconfig.json:
```diff
{
  "compilerOptions": {
    "strict": true,
+   "skipLibCheck": true,
    ...
  }
}
```
Explicação: somente usar se erros vierem de tipos de bibliotecas; NÃO substituirá correções de tipo internas.
