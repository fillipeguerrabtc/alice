- Há também checagens no deploy para GH_PAT e PostgreSQL, mas o erro crítico nesta execução é o alice-chat não estar saudável.

O que você precisa fazer (passos ordenados)
1. Conectar no servidor onde o docker compose roda e inspecionar os logs do container alice-chat.
2. Identificar a causa raiz do crash/unhealthy consultando logs da aplicação e o resultado do healthcheck.
3. Corrigir a causa (variáveis de ambiente faltando, endpoint /health inexistente, falha na conexão ao banco, dependências não instaladas, etc.).
4. Harden o docker-compose / Dockerfile com um healthcheck apropriado e (se necessário) um script de espera para o Postgres.
5. Ajustar o workflow / secrets para garantir GH_PAT e variáveis essenciais chegarem ao servidor.

Comandos práticos para diagnosticar agora (execute no servidor de produção)
- Ver status dos containers:
  docker ps --format "table {{.Names}}\t{{.Status}}"
- Logs do container problemático (últimas 200 linhas):
  docker logs alice-chat --tail 200
- Seguir logs em tempo real:
  docker logs -f alice-chat
- Ver informação do healthcheck:
  docker inspect --format '{{json .State.Health}}' alice-chat
- Ver logs do compose (todos serviços):
  docker compose -f docker-compose.prod.yml logs --tail 200
- (Se quiser reiniciar apenas o serviço para testar):  
  docker compose -f docker-compose.prod.yml up -d --no-deps --build alice-chat

O que procurar nos logs
- Tracebacks/stack traces da aplicação (missing module, erro de SQL, mismatched env var).
- Mensagens do healthcheck da imagem (se o healthcheck falhar, por que).
- Erro de conexão com PostgreSQL (timeout, auth failed, host incorreto).
- Erros de permissão/arquivo ausente no container.

Soluções típicas e exemplos de código

A) Se o health endpoint não existe / está incorreto
- Crie /health (ou /ready) na sua aplicação que devolva 200 OK quando estiver pronta (DB ok, dependências ok).
- Exemplo (Node/Express):
  app.get('/health', async (req, res) => {
    const dbOk = await checkDbConnection(); // implemente
    if (dbOk) return res.status(200).send('OK');
    return res.status(503).send('DB unavailable');
  });

B) Healthcheck em docker-compose (melhora resistência)
- Edite docker-compose.prod.yml para algo assim (use o ref do commit se for linkar arquivos: ref 4520d1563b5a10b2835f44aa92dedc9a1d35d28e):
  alice-chat:
    image: myrepo/alice-chat:${IMAGE_TAG}
    environment:
      - DATABASE_URL=${DATABASE_URL}
      - PGHOST=${PGHOST}
      - PGUSER=${PGUSER}
      - PGPASSWORD=${PGPASSWORD}
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8080/health || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 30s
    restart: on-failure
    depends_on:
      - alice-postgres

Explicação:
- start_period evita que o healthcheck conte falhas enquanto o container está fazendo boot.
- retries/interval aumentam tolerância a atrasos de startup.

C) Se a aplicação precisa do Postgres disponível antes de iniciar
- Adicione um pequeno entrypoint que aguarde o Postgres (pg_isready) e depois inicie a aplicação:
  1) Adicionar no Dockerfile (exemplo Alpine / Debian):
     RUN apk add --no-cache postgresql-client    # (ou apt-get install -y postgresql-client)
  2) entrypoint.sh:
     #!/bin/sh
     set -e
     echo "Aguardando Postgres em ${PGHOST}:${PGPORT:-5432}..."
     until pg_isready -h "${PGHOST}" -p "${PGPORT:-5432}" -U "${PGUSER}"; do
       echo "Postgres não pronto, aguardando 2s..."
       sleep 2
     done
     echo "Postgres pronto, iniciando app..."
     exec "$@"
  3) Dockerfile:
     COPY entrypoint.sh /entrypoint.sh
     RUN chmod +x /entrypoint.sh
     ENTRYPOINT ["/entrypoint.sh"]
     CMD ["npm","start"]   # ou o comando da sua app

D) Healthcheck que valida também a conexão com DB (melhora confiança)
- healthcheck script (healthcheck.sh) dentro da imagem:
  #!/bin/sh
  # checa endpoint HTTP e conexão DB
  if ! curl -sSf http://localhost:8080/health >/dev/null 2>&1; then
    exit 1
  fi
  # opcional: test DB simples
  if ! pg_isready -h "${PGHOST}" -p "${PGPORT:-5432}" -U "${PGUSER}" >/dev/null 2>&1; then
    exit 1
  fi
  exit 0

No docker-compose:
  healthcheck:
    test: ["CMD-SHELL", "/app/healthcheck.sh"]
    interval: 30s
    timeout: 10s
    retries: 5
    start_period: 30s

E) Garantir que secrets cheguem (GH_PAT)
- Verifique se o GH_PAT está definido no repositório: Settings > Secrets and variables > Actions.
- No workflow .github/workflows/deploy-production.yml, certifique-se de exportar/usar o secret e passá-lo ao servidor. Exemplo de step SSH (varia com a action usada):
  - name: Deploy via SSH
    uses: appleboy/ssh-action@master
    with:
      host: ${{ secrets.SERVER_HOST }}
      username: ${{ secrets.SERVER_USER }}
      key: ${{ secrets.SERVER_SSH_KEY }}
      envs: GH_PAT=${{ secrets.GH_PAT }}
      script: |
        echo "GH_PAT length: ${#GH_PAT}"
        export GH_PAT="${GH_PAT}"
        docker compose -f docker-compose.prod.yml pull
        docker compose -f docker-compose.prod.yml up -d --remove-orphans

- Se seu script de deploy roda via SSH e espera variáveis no ambiente, passe-as explicitamente como acima. Caso use um outro método, garanta que GH_PAT seja interpolado no .env no servidor antes do docker compose.

Lista de verificação priorizada (faça nessa ordem)
1. Rode docker logs alice-chat e cole as últimas mensagens de erro.
2. Se houver erro de falta de env var (por exemplo DB_URL/PGUSER), corrija no docker-compose.prod.yml e no workflow que envia variáveis.
3. Se a aplicação falha por não conseguir conectar ao DB, adicione entrypoint que aguarde o Postgres.
4. Adicione ou corrija o endpoint /health e alinhe healthcheck no compose.
5. Aumente start_period/retries se o serviço demora para iniciar.
6. Reimplante e monitore: docker compose -f docker-compose.prod.yml up -d e depois docker ps / docker inspect health.
